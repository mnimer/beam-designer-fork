## Credential Handling Rules (GLOBAL - applies to every transform)

Credentials are never stored inline in the pipeline definition. A node configures
authentication in one of two ways, and you MUST inspect each node's properties to tell
them apart:

1. **Secret Manager reference (preferred).** The node has `authMode: secretManager` and/or
   a property whose name ends in `Secret` -- for example `passwordSecret`,
   `accessKeySecret` -- or a `secretName` property. The VALUE of that property is the
   SHORT ID of a Google Cloud Secret Manager secret. It is NOT the credential.
   - You MUST generate code that resolves the secret at runtime.
   - Required import: `com.google.cloud.secretmanager.v1.SecretManagerServiceClient`,
     `com.google.cloud.secretmanager.v1.SecretVersionName`
   - Required Maven dependency:
     ```xml
     <dependency>
       <groupId>com.google.cloud</groupId>
       <artifactId>google-cloud-secretmanager</artifactId>
     </dependency>
     ```
     (the `libraries-bom` already manages its version if present; otherwise pin one)
   - Resolve the secret ONCE at pipeline construction time, in `main`, never inside a
     `DoFn`. A `DoFn` runs per element and per worker, and `SecretManagerServiceClient`
     is not serializable -- fetching there would both break serialization and issue one
     API call per record.
   - Use this shape:
     ```java
     /** Reads the payload of a Secret Manager secret. */
     private static String accessSecret(String projectId, String secretId) throws IOException {
       try (SecretManagerServiceClient client = SecretManagerServiceClient.create()) {
         SecretVersionName name = SecretVersionName.of(projectId, secretId, "latest");
         return client.accessSecretVersion(name).getPayload().getData().toStringUtf8();
       }
     }
     ```
   - Assign the resolved value to a `final String` local in `main` and pass that into the
     transform where the plaintext property would otherwise have gone. For example, a
     JdbcIO node with `passwordSecret: prod-db-pw` becomes
     `.withPassword(accessSecret(projectId, "prod-db-pw"))`.
   - Derive `projectId` from the pipeline options (`options.getProject()`). Do NOT hardcode it.

2. **Plaintext (discouraged, legacy).** The node has `authMode: plaintext` or simply a
   `password` property with no corresponding `passwordSecret`. Use the value as given.

**MUTUAL EXCLUSION**: never emit both. If a node has a `*Secret` reference, ignore any
plaintext property of the same name and use the Secret Manager path.

**REDACTED VALUES**: if a property value is exactly `__REDACTED_BY_BEAM_DESIGNER__`, that is
a placeholder, not a credential. Never emit it as a string literal. Read the value from an
environment variable named after the property in upper snake case via `System.getenv(...)`
and add a brief comment noting that the operator must supply it.

## 3. Core Architecture & Coding Rules

### A. Runtime Variables vs. Hardcoded Node Configuration
- **STRICT RUNTIME VARIABLES ONLY**:
  - ONLY variables explicitly declared under `runtimeVariables` in the YAML (e.g. `JOB_ID`, `NUM_OBJECTS_PER_ITERATION`) may be declared in the `PipelineOptions` interface, in `metadata.json`, and as CLI arguments in runner scripts.
  - **HARDCODE ALL NODE PROPERTIES**: All node configuration values (JDBC URLs, usernames, passwords, driverClassName, SQL queries, table names, fetch/batch sizes, delimiters, file patterns, BigQuery tables, Pub/Sub topics) MUST be hardcoded directly into transform calls in Java. NEVER expose node properties as `PipelineOptions`.
- **Reserved Option Name Safety & Remapping**:
  - **NEVER use reserved Beam option names**: `jobId`, `jobName`, `project`, `tempLocation`, `gcpTempLocation`, `runner`, `appName` are reserved by Apache Beam / Dataflow. Declaring `getJobId()` in a custom `PipelineOptions` interface causes fatal `IllegalArgumentException: Expected getter for property [jobId] to be marked with @Default on all ... DataflowWorkerHarnessOptions`.
  - If a runtime variable is named `JOB_ID` or `job_id`, map its identifier to `pipelineJobId` consistently across ALL artifacts:
    - `PipelineOptions` interface: `String getPipelineJobId(); void setPipelineJobId(String value);`
    - `metadata.json` parameter `"name"`: `"pipelineJobId"`
    - `run_directrunner.sh` arguments: `--pipelineJobId="value"`
    - `run_sparkrunner.sh` arguments: `--pipelineJobId="value"`
    - `run_dataflowrunner.sh` parameters: `pipelineJobId="value"`
  - Convert all other runtime variables from YAML into standard camelCase (e.g. `NUM_OBJECTS_PER_ITERATION` -> `numObjectsPerIteration`, getter: `getNumObjectsPerIteration()`, setter: `setNumObjectsPerIteration(Integer value)`).
  - Use standard typed getters/setters on `PipelineOptions`. Do NOT use `ValueProvider<T>` (deprecated legacy Classic template API).
  - Ensure that ALL runtime variables defined in YAML are supplied with default values in `run_directrunner.sh`, `run_dataflowrunner.sh`, and `run_sparkrunner.sh`.

### B. Node Instruction Fields vs Hardcoded Config
- `data.system_instructions` and `data.properties.codeGenerationPrompt` (or `data.properties.prompt`) contain natural-language descriptions of the logic this node must implement.
  - Treat them as implementation instructions: generate Java code that fulfills them.
  - NEVER emit them as string literals, configuration values, or comment-only stubs.
  - They are EXEMPT from the "hardcode all node properties" rule.
  - If they conflict with default behaviors in the reference table below, the node's instructions win.
- **NO SCHEMA GUESSING / HALLUCINATION**: Do NOT invent, assume, or hardcode payload schema fields based on topic, subscription, dataset, or table names (for example, do NOT assume a subscription named with "object-finalize" carries specific GCS file metadata keys like `bucket`, `name`, `size`, `timeCreated`). Unless explicit schema fields are specified in `system_instructions` or `codeGenerationPrompt`, ALWAYS parse payloads generically across all fields.

### C. Runtime Variable Interpolation
- Any `${VAR_NAME}` token inside a node's properties or instructions refers to the runtime variable `VAR_NAME` from `runtimeVariables`.
- Replace it with a read of the corresponding `PipelineOptions` getter using camelCase (e.g. `${NUM_OBJECTS_PER_ITERATION}` -> `options.getNumObjectsPerIteration()`). NEVER hardcode the default value of an interpolated `${VAR_NAME}`.

### D. Custom `DoFn` Policy
- **PREFER BUILT-IN TRANSFORMS**: If a node's `beam_transform` appears in the SDK Syntax Reference below, use that built-in `PTransform`. Do NOT reimplement it as a custom `DoFn`.
- **WHEN A CUSTOM `DoFn` IS REQUIRED**: Write a custom `DoFn` ONLY in these cases:
  1. `beam_transform` is `ParDo` or `ParseMessage` (multi-output branching parser).
  2. The node has `system_instructions` or `codeGenerationPrompt` describing custom business logic.
  3. A built-in transform requires a user-supplied function argument (`Filter.by`, `MapElements.via`, `WithKeys.of`, `JdbcIO.PreparedStatementSetter`/`RowMapper`), or type adaptation is needed between two built-ins.
- Define custom `DoFn` classes as `static` nested classes inside the main pipeline class, or as concise inline lambdas. Do NOT create separate helper source files.

### E. Type Propagation & End-to-End Edge Compatibility
- **MANDATORY EDGE TYPE ALIGNMENT**: Every edge in the input YAML connects a `source` node to a `target` node. When generating code, you MUST inspect both:
  1. **Upstream Output Type ($T_{in}$)**: The Java type emitted by the predecessor node (see Section 4).
  2. **Downstream Expected Input Type ($T_{out}$)**: The Java type consumed by the successor node (see Section 4).
- **Intermediate Transform Bridging**: Any intermediate step (`ParseMessage`, `ParDo`, `Map`, `Filter`) MUST explicitly bridge $T_{in} \rightarrow T_{out}$ to match the downstream connector's expected input type as defined in Section 4. (For example, BigQuery sinks require `TableRow`, Kafka sinks require `KV<K, V>`, Parquet sinks require `GenericRecord`, Text/PubSub sinks require `String`, etc.).
- **Automatic Adapters for Direct Incompatible Edges**: If an edge in the YAML directly connects a source to a sink with incompatible types without an intermediate transformation (e.g. `PubsubIO.readStrings()` producing `String` connected directly to `BigQueryIO.writeTableRows()` requiring `TableRow`), you MUST automatically insert a clean mapping step (such as `MapElements` converting `String` to `TableRow`) between them so the Java pipeline is strictly type-safe and compilable.

### F. Transform Naming & Uniqueness
- Every step name in `.apply("<step_name>", ...)` MUST be non-empty and **globally unique** across the pipeline.
- Use `data.label` as the step name. If multiple nodes share the same label or if the label equals the default transform name, append a distinct qualifier or node ID (e.g. `Filter Valid Records (node_2)`) to prevent `IllegalArgumentException: A transform with name '...' already exists in the pipeline`.

### G. Streaming vs. Batch Detection
- If the pipeline contains streaming sources (`PubsubIO`, `KafkaIO`, `MqttIO`, `PeriodicImpulse`, unbounded `GenerateSequence`), configure the pipeline for streaming:
  - Pass `--streaming=true` in `run_directrunner.sh`.
  - When creating `PipelineOptions`, ensure streaming options can be configured.

### H. Separation of Runner Scripts and Unit Tests
- `run_directrunner.sh`, `run_dataflowrunner.sh`, and `run_sparkrunner.sh` MUST ONLY execute the main pipeline class. They must **NEVER** run unit tests (`mvn test`).
- Unit tests live strictly in `src/test/java/com/example/<PipelineName>Test.java` and use Beam's `TestPipeline` and `PAssert`.

### I. Code Documentation & Quality
- Include author and class documentation header on the main class:
  ```java
  /**
   * Pipeline: <PipelineName>
   * Description: <Pipeline Description>
   * Author: Mike Nimer <mikenimer@google.com>
   */
  ```
- Fail fast: Do NOT add undocumented fallbacks or silently swallow exceptions.

  - `faker.timeAndDate()` returns `net.datafaker.providers.base.TimeAndDate`; `past(long, TimeUnit)` returns `java.time.Instant`, whose `toString()` is ISO-8601 (`2025-03-12T10:15:30Z`).   - `faker.date()` returns `net.datafaker.providers.base.DateAndTime`; `past(int, TimeUnit)` returns `java.sql.Timestamp`, whose `toString()` is space-separated (`2025-03-12 10:15:30.123`), NOT ISO-8601.
