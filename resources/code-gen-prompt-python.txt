## Credential Handling Rules (GLOBAL - applies to every transform)

Credentials are never stored inline in the pipeline definition. A node configures
authentication in one of two ways, and you MUST inspect each node's properties to tell
them apart:

1. **Secret Manager reference (preferred).** The node has `authMode: secretManager` and/or
   a property whose name ends in `Secret` -- for example `passwordSecret`,
   `accessKeySecret` -- or a `secretName` property. The VALUE of that property is the
   SHORT ID of a Google Cloud Secret Manager secret. It is NOT the credential.
   - You MUST generate code that resolves the secret at runtime.
   - Required import: `from google.cloud import secretmanager`
   - Add `google-cloud-secret-manager` to `requirements.txt`.
   - Resolve the secret ONCE during pipeline construction, never per element. Fetching
     inside a `DoFn` would issue one API call per record.
   - Use this shape:
     ```python
     def _access_secret(project_id: str, secret_id: str, version: str = "latest") -> str:
         """Reads the payload of a Secret Manager secret."""
         client = secretmanager.SecretManagerServiceClient()
         name = f"projects/{project_id}/secrets/{secret_id}/versions/{version}"
         return client.access_secret_version(request={"name": name}).payload.data.decode("UTF-8")
     ```
   - Pass the resolved value into the transform where the plaintext property would
     otherwise have gone. For example, a JdbcIO node with `passwordSecret: prod-db-pw`
     becomes `password=_access_secret(project_id, "prod-db-pw")`.
   - Derive `project_id` from the pipeline options / `--project` argument. Do NOT hardcode it.

2. **CLI Arguments / Parameterized Credentials (when credentials exist in YAML properties)**:
   - **CRITICAL ZERO-PLAINTEXT MANDATE**: NEVER embed plaintext database passwords, connection secrets, auth tokens, or private keys as string literals in Python source code or `ReadFromJdbc` / `WriteToJdbc` calls (e.g. NEVER write `password="dbpswrd123"` or `username="dbuser123"`).
   - **NO DEFAULT VALUES ON PASSWORDS**: NEVER specify default values for passwords in `parser.add_argument(...)` (e.g. do NOT use `default='dbpswrd123'`). Use `required=True` instead so passwords must be explicitly provided at runtime.
   - When a node specifies authentication properties (such as `password`, `username`, or connection strings) directly in YAML without a `*Secret` reference:
     - **Parameterize via `argparse` / `PipelineOptions`**: Expose these credential properties as CLI arguments in the argument parser (e.g. `parser.add_argument('--source_db_username', required=True, ...)`, `parser.add_argument('--source_db_password', required=True, ...)`, and similarly for sink nodes, e.g. `parser.add_argument('--sink_db_username', required=True, ...)`, `parser.add_argument('--sink_db_password', required=True, ...)`, or `--db_username` / `--db_password` if a single DB).
     - Pass the values from `known_args` into the transform (e.g. `username=known_args.source_db_username, password=known_args.source_db_password`).
     - Declare the corresponding parameters in `metadata.json` under `parameters` (marked `"isOptional": false`).
     - **NO FALLBACK STRINGS IN RUNNER SCRIPTS**: Do NOT include hardcoded fallback strings for sensitive passwords or tokens in runner shell scripts (e.g. NEVER write `PASSWORD=${PASSWORD:-'dbpswrd123'}`). Instead, check for the required environment variable, exiting with an error if unset:
       ```bash
       : "${SOURCE_DB_PASSWORD:?Error: SOURCE_DB_PASSWORD environment variable must be set}"
       ```
       Then pass `--source_db_password="${SOURCE_DB_PASSWORD}"` (usernames or non-sensitive identifiers can use standard fallbacks like `${SOURCE_DB_USERNAME:-dbuser123}`).
     - This rule is an explicit exception to the "only runtimeVariables in CLI arguments" rule: sensitive credentials MUST be parameterized via CLI arguments to ensure zero plaintext secrets in code and scripts.

**MUTUAL EXCLUSION**: never emit both. If a node has a `*Secret` reference, ignore any
plaintext property of the same name and use the Secret Manager path.

**REDACTED VALUES**: if a property value is exactly `__REDACTED_BY_BEAM_DESIGNER__`, that is
a placeholder, not a credential. Never emit it as a string literal. Read the value from an
environment variable named after the property in upper snake case and add a brief comment
noting that the operator must supply it.

## 3. Core Architecture & Coding Rules

### A. Runtime Variables vs. Hardcoded Node Configuration
- **RUNTIME VARIABLES & SENSITIVE CREDENTIAL PARAMETERIZATION**:
  - Command-line arguments, `metadata.json`, and runner scripts MUST include:
    1. All variables explicitly declared under `runtimeVariables` in the YAML (e.g. `JOB_ID`, `NUM_OBJECTS_PER_ITERATION`).
    2. Any sensitive credentials (such as JDBC database passwords and usernames) present in node properties, parameterized as described in the Credential Handling Rules above.
  - **HARDCODE NON-SENSITIVE NODE PROPERTIES**: Non-sensitive node configuration values (JDBC driverClassName, SQL queries, table names, fetch/batch sizes, delimiters, file patterns, BigQuery tables, Pub/Sub topics) MUST be hardcoded directly into transform calls in Python. NEVER expose non-sensitive properties as CLI arguments. NEVER hardcode passwords or sensitive credentials directly in code.
- **Reserved Option Name Safety & Remapping**:
  - **NEVER use reserved Beam/Dataflow option names**: `job_name`, `job_id`, `project`, `region`, `runner`, `temp_location`, `staging_location`, `template_location`, `streaming`, `subnetwork` are reserved by Apache Beam / Dataflow.
  - If a runtime variable is named `JOB_ID` or `job_id`, map its identifier to `pipeline_job_id` consistently across ALL artifacts:
    - `argparse` parameter: `parser.add_argument('--pipeline_job_id', ...)`
    - `metadata.json` parameter `"name"`: `"pipeline_job_id"`
    - `run_directrunner.sh` argument: `--pipeline_job_id="value"`
    - `run_dataflowrunner.sh` parameter: `pipeline_job_id="value"`
  - Convert all other runtime variables from YAML into standard snake_case (e.g. `NUM_OBJECTS_PER_ITERATION` -> `num_objects_per_iteration`).
  - For Flex Templates, use standard `parser.add_argument(...)`. **NEVER** use `parser.add_value_provider_argument(...)` (deprecated legacy Classic template API that causes runtime `TypeCheckError`).
  - Ensure that ALL runtime variables defined in YAML are supplied with default values in `run_directrunner.sh` and `run_dataflowrunner.sh`.

### B. Node Instruction Fields vs Hardcoded Config
- `data.system_instructions` and `data.properties.codeGenerationPrompt` (or `data.properties.prompt`) contain natural-language descriptions of the logic this node must implement.
  - Treat them as implementation instructions: generate Python code that fulfills them.
  - NEVER emit them as string literals, configuration values, or comment-only stubs.
  - They are EXEMPT from the "hardcode all node properties" rule.
  - If they conflict with default behaviors in the reference table below, the node's instructions win.
- **NO SCHEMA GUESSING / HALLUCINATION**: Do NOT invent, assume, or hardcode payload schema fields based on topic, subscription, dataset, or table names (for example, do NOT assume a subscription named with "object-finalize" carries specific GCS file metadata keys like `bucket`, `name`, `size`, `timeCreated`). Unless explicit schema fields are specified in `system_instructions` or `codeGenerationPrompt`, ALWAYS parse payloads generically across all fields.

### C. Runtime Variable Interpolation
- Any `${VAR_NAME}` token inside a node's properties or instructions refers to the runtime variable `VAR_NAME` from `runtimeVariables`.
- Replace it with a read of the corresponding parsed CLI argument using snake_case (e.g. `${NUM_OBJECTS_PER_ITERATION}` -> `known_args.num_objects_per_iteration`). NEVER hardcode the default value of an interpolated `${VAR_NAME}`.

### D. Custom `DoFn` Policy
- **PREFER BUILT-IN TRANSFORMS**: If a node's `beam_transform` appears in the SDK Syntax Reference below, use that built-in `PTransform`. Do NOT reimplement it as a custom `DoFn`.
- **WHEN A CUSTOM `DoFn` OR FUNCTION IS REQUIRED**: Write a custom `beam.DoFn` or function ONLY in these cases:
  1. `beam_transform` is `ParDo` or `ParseMessage` (multi-output branching parser).
  2. The node has `system_instructions` or `codeGenerationPrompt` describing custom business logic.
  3. A built-in transform requires a user-supplied callable (`beam.Filter`, `beam.Map`, `beam.FlatMap`, or adapter lambdas between built-ins).
- Define custom `beam.DoFn` classes or functions in the main pipeline module. Do NOT create separate helper source files.

### E. Type Propagation & End-to-End Edge Compatibility
- **MANDATORY EDGE TYPE ALIGNMENT**: Every edge in the input YAML connects a `source` node to a `target` node. When generating code, you MUST inspect both:
  1. **Upstream Output Type ($T_{in}$)**: The Python type emitted by the predecessor node (see Section 4).
  2. **Downstream Expected Input Type ($T_{out}$)**: The Python type consumed by the successor node (see Section 4).
- **Intermediate Transform Bridging**: Any intermediate step (`ParseMessage`, `ParDo`, `Map`, `Filter`) MUST explicitly bridge $T_{in} \rightarrow T_{out}$ to match the downstream connector's expected input type as defined in Section 4. (For example, BigQuery sinks require `dict`, Kafka sinks require `(key, value)` tuples, Parquet sinks require PyArrow record dicts, Text sinks require `str`, PubSub sinks require `bytes`, etc.).
- **Automatic Adapters for Direct Incompatible Edges**: If an edge in the YAML directly connects a source to a sink with incompatible types without an intermediate transformation (e.g. `ReadFromPubSub` producing `bytes` connected directly to `WriteToBigQuery` requiring `dict`), you MUST automatically insert a clean mapping step (such as `beam.Map` decoding and converting JSON bytes to `dict`) between them so the Python pipeline is strictly type-safe.

### F. Transform Naming & Uniqueness
- Every step name in `p | '<step_name>' >> ...` MUST be non-empty and **globally unique** across the pipeline.
- Use `data.label` as the step name. If multiple nodes share the same label or if the label equals the default transform name, append a distinct qualifier or node ID (e.g. `'Filter Valid Records (node_2)'`) to prevent `RuntimeError: A transform with label "..." already exists in the pipeline`.

### G. Streaming vs. Batch Detection
- If the pipeline contains streaming sources (`PubSubIO`, `KafkaIO`, `MqttIO`, `PeriodicImpulse`), configure the pipeline for streaming:
  - Add `options.view_as(StandardOptions).streaming = True` when initializing `PipelineOptions` or pass `--streaming` in `run_directrunner.sh`.

### H. Separation of Runner Scripts and Unit Tests
- `run_directrunner.sh` and `run_dataflowrunner.sh` MUST ONLY execute the main pipeline file (`python src/<pipeline_name>.py ... "$@"`). They must **NEVER** run unit tests (`unittest`).
- The main pipeline file `src/<pipeline_name>.py` MUST have `if __name__ == '__main__': run()` and MUST **NEVER** import `unittest` or invoke `unittest.main()`.
- Unit tests live strictly in `src/<pipeline_name>_test.py` and use Beam's `TestPipeline`, `assert_that`, and `equal_to`. Import the pipeline module using `from src.<pipeline_name> import ...` or `from <pipeline_name> import ...`.

### I. Code Documentation & Quality
- Include author and module documentation header on the main file:
  ```python
  """
  Pipeline: <PipelineName>
  Description: <Pipeline Description>
  Author: Mike Nimer <mikenimer@google.com>
  """
  ```
- Fail fast: Do NOT add undocumented fallbacks or silently swallow exceptions.

## 4. Built-in Beam Transform Syntax & Import Reference

### 1. Sources & Sinks (I/O Connectors)
- **`PubSubIO`**:
  - Required Imports: `import apache_beam as beam`
  - Source: `beam.io.ReadFromPubSub(subscription=..., topic=...)` (produces `bytes`)
  - Sink: `beam.io.WriteToPubSub(topic=...)` (consumes `bytes`)
- **`GenerateSequence`**:
  - **CRITICAL — PREFER `PeriodicImpulse` FOR PERIODIC TRIGGERS**: `GenerateSequence` has **no native Python implementation**. It is a Java transform reached over cross-language expansion, which means it requires (a) downloading an ~800MB Java expansion-service JAR and (b) **a running Docker daemon** to host the Java SDK harness that actually executes it. On a developer machine without Docker the pipeline starts, logs unrelated JVM noise from every connector bundled in the shadowJar (e.g. `Running JvmInitializer#beforeProcessing for ...KafkaIOInitializer`), and **produces no elements**.
    - Therefore, when the node is only being used as a **periodic trigger / tick source** (i.e. the emitted numbers are discarded and downstream only needs "fire every N seconds"), you **MUST** generate `PeriodicImpulse` instead. It is pure Python, needs no JVM and no Docker:
      ```python
      import time
      from apache_beam.transforms.periodicsequence import PeriodicImpulse

      trigger_stream = p | 'trigger' >> PeriodicImpulse(
          start_timestamp=time.time(),
          fire_interval=period_seconds,   # seconds, NOT milliseconds
      )
      ```
    - To fan out N elements per tick: `| 'fan out' >> beam.FlatMap(lambda ts: range(elements_per_period))`.
    - If bounded without rate limit and purely local in-memory: `beam.Create(range(start, stop))`.
    - Only fall through to the cross-language forms below when the pipeline genuinely consumes the **sequence values themselves** (e.g. the numbers are used as keys or IDs) and a periodic tick is not sufficient.
  - Required Imports (cross-language forms only): `from apache_beam.transforms.external import ExternalTransform, ImplicitSchemaPayloadBuilder, BeamJarExpansionService` (and optionally `from apache_beam.io.external.generate_sequence import GenerateSequence` for non-rate-limited bounded sequences).
  - **CRITICAL RATE LIMITING & PERIOD RULE**:
    - Python SDK's helper class `GenerateSequence.__init__` omitted the `period` parameter in its constructor, so calling `GenerateSequence(elements_per_period=1)` causes the Java expansion service to throw `java.lang.IllegalArgumentException: elements per period specified, but no period specified`.
    - Therefore, when rate limiting or period is configured (e.g. `elementsPerPeriod` or `periodSeconds`), you **MUST** use `ExternalTransform('beam:external:java:generate_sequence:v1', ...)` with `ImplicitSchemaPayloadBuilder` supplying both `elements_per_period` AND `period` in milliseconds (`periodSeconds * 1000`):
      ```python
      ExternalTransform(
          'beam:external:java:generate_sequence:v1',
          ImplicitSchemaPayloadBuilder({
              'start': start,
              'stop': stop, # None for unbounded
              'elements_per_period': elements_per_period,
              'period': period_seconds * 1000, # period in milliseconds
          }),
          BeamJarExpansionService('sdks:java:io:expansion-service:shadowJar')
      )
      ```
    - NOTE: `ImplicitSchemaPayloadBuilder` **silently drops any key whose value is `None`**, so `'stop': None` is simply absent from the payload and correctly yields an unbounded sequence. Do not attempt to pass `-1` or `0` to mean "unbounded".
  - Bounded without Rate Limiting (start to stop):
    ```python
    from apache_beam.io.external.generate_sequence import GenerateSequence
    from apache_beam.transforms.external import BeamJarExpansionService

    GenerateSequence(start=start, stop=stop, expansion_service=BeamJarExpansionService('sdks:java:io:expansion-service:shadowJar'))
    ```
  - Unbounded / Streaming with Rate Limiting (e.g., start=1, 1 element every 15s):
    ```python
    from apache_beam.transforms.external import ExternalTransform, ImplicitSchemaPayloadBuilder, BeamJarExpansionService

    ExternalTransform(
        'beam:external:java:generate_sequence:v1',
        ImplicitSchemaPayloadBuilder({
            'start': 1,
            'stop': None,
            'elements_per_period': 1,
            'period': 15000, # 15 seconds in milliseconds
        }),
        BeamJarExpansionService('sdks:java:io:expansion-service:shadowJar')
    )
    ```

### 4. Windowing, Utility & Dangling Outputs
- **`WindowInto`**:
  - Required Imports: `from apache_beam import window`
  - Syntax: `beam.WindowInto(window.FixedWindows(size_in_seconds))`
- **`ParseMessage`**:
  - Required Imports: `import json`, `from apache_beam import pvalue`
  - Tagged Outputs: If downstream edges connect to `valid` and `error` handles, implement a `beam.DoFn`:
    ```python
    class ParseMessageDoFn(beam.DoFn):
        def process(self, element):
            try:
                # Handle bytes or string payload
                msg_str = element.decode('utf-8') if isinstance(element, bytes) else str(element)
                data = json.loads(msg_str)
                # Generic JSON Parsing: emit data dictionary directly
                yield pvalue.TaggedOutput('valid', data)
            except Exception as e:
                yield pvalue.TaggedOutput('error', {'error': str(e), 'raw': str(element)})
    ```
    Apply via `p | 'Parse Message' >> beam.ParDo(ParseMessageDoFn()).with_outputs('valid', 'error')`.
  - **GENERIC JSON PARSING RULE (CRITICAL)**: When parsing JSON (for BigQuery or general processing) and NO explicit schema is defined in `codeGenerationPrompt` or `system_instructions`, **ALWAYS parse all JSON fields dynamically into a `dict`** (`json.loads(...)`). **NEVER** hardcode specific field names (such as `bucket`, `name`, `size`, `timeCreated`) based on topic or subscription names!
- **`LogMessage`**:
  - Required Imports: `import logging`
  - Syntax: Define a passthrough logger so elements are preserved:
    ```python
    def _log_element(element):
        logging.info("Log: %s", element)
        return element

    | 'Log Message' >> beam.Map(_log_element)
    ```
  - **NEVER** use `print(...) or logging.info(...)` in a lambda because both return `None`, silently destroying downstream data.
- **`Flatten`**:
  - Syntax: `(pcoll1, pcoll2) | beam.Flatten()`
- **`Reshuffle`**:
  - Syntax: `beam.Reshuffle()`
- **Global Fallback Rule**: If a transform requires a function argument that the node's properties and instructions do not specify, generate an identity/pass-through implementation with a `# TODO:` comment. Never invent business logic.
- **Dangling Branches**: If a node produces a `PCollection` that no downstream edge consumes, append a simple logging step so the branch terminates cleanly in a sink.

## 7. Final Self-Review Checklist
Before outputting the final JSON `files` array, verify:
1. No literal `{{...}}` placeholder remains in any generated file.
2. `{{pipeline_name}}` is rendered in snake_case, and `src/<module>.py`, the Dockerfile `FLEX_TEMPLATE_PYTHON_PY_FILE`, `run_directrunner.sh`, and unit test imports all agree.
3. Every runtime variable uses the identical snake_case name across CLI argument parser, `metadata.json`, and both runner scripts.
4. No CLI option uses a reserved Beam name (`job_name`, `job_id`, `project`, `temp_location`, `staging_location`, `runner`, `region`).
5. All imports are present; `requirements.txt` contains compatible package bounds (`apache-beam[gcp]>=2.55.0,<3.0.0`).
6. `src/__init__.py` is generated as an empty file.
7. `src/<pipeline_name>.py` has `if __name__ == '__main__': run()` and never calls `unittest.main()`.
8. Every `?` in a JDBC SQL statement matches the upstream tuple element count 1-to-1.
9. Every transform step name in `p | '<step_name>' >> ...` is globally unique.
10. Sinks receive their required type (e.g. `bytes` for Pub/Sub and MQTT, `dict` for BigQuery, `(k, v)` tuples for Kafka), with bridging steps where needed.
11. No logging lambda returns `None` where elements must flow downstream.
12. For streaming pipelines, `--streaming` is passed in `run_directrunner.sh`.
13. No hardcoded credentials: No database passwords, tokens, or sensitive credentials appear as string literals in Python source code or as `default=` values in `parser.add_argument(...)`. Runner scripts must NOT use hardcoded fallback strings for secrets (use `: "${DB_PASSWORD:?Error: ...}"`).
14. Dockerfile base images use explicit pinned version tags (e.g. `:1.1`), never mutable `:latest`. Runner scripts use parameterized `${IMAGE_TAG:-latest}` for image tags. Dockerfile configures container hardening permissions (`RUN chmod -R a+rx /template`).
15. `.dockerignore` is generated to exclude `.git`, `venv`, `*.log`, and `__pycache__` from the Docker build context.

### Python Projects
- **Python 3.12+ Compatibility**: In `requirements.txt`, specify `apache-beam[gcp]>=2.74.0` (do NOT pin old packages requiring deprecated `pkg_resources`). Do NOT include `pyspark`.
- **Package Marker**: Always generate `src/__init__.py`.
- **Pipeline Options & Argument Parsing**: Always use standard `parser.add_argument(...)` when defining custom `PipelineOptions` or `argparse`. **NEVER** use `parser.add_value_provider_argument(...)` because `RuntimeValueProvider` is for legacy Classic templates and breaks Beam type checking on transforms like `fileio.MatchFiles` (causes `TypeCheckError`).
- **FileIO Imports**: When using FileIO (`MatchFiles`, `ReadMatches`, `WriteToFiles`), always include `from apache_beam.io import fileio` because `apache_beam.io` does not automatically expose `fileio` as an attribute on `beam.io` without an explicit import.
- **JdbcIO Cross-Language Driver Classpath**: When connecting to MySQL, SQL Server, Oracle, SQLite, or Derby via `ReadFromJdbc` / `WriteToJdbc`, always supply the corresponding Maven coordinate in `classpath=[...]` so the Beam Java expansion service loads the JDBC driver.
- **JdbcIO Write Statement Placeholders**: When using `statement` with `WriteToJdbc`, always ensure the number of columns in the SQL statement, the number of `?` placeholders, and the number of tuple items yielded by the upstream `DoFn` match 1-to-1.
- **Unit Test Imports**: In unit tests, import the pipeline module using `from src.<pipeline_name> import ...` or `from <pipeline_name> import ...`.
- **Tagged Outputs — NEVER wrap the main output in `TaggedOutput`**: This silently discards every element. Beam routes an unrecognised tag to a null receiver, so there is **no error, no warning, and no output** — the pipeline runs to completion emitting nothing, which is extremely hard to debug.
  - When a `DoFn` has multiple outputs, `yield` the main output **bare** and wrap only the additional outputs:
    ```python
    TAG_ERRORS = 'errors'

    class MyDoFn(beam.DoFn):
        def process(self, element):
            try:
                yield transform(element)                              # CORRECT: main output, bare
            except Exception as e:
                yield TaggedOutput(TAG_ERRORS, {'error': str(e)})     # CORRECT: additional output

    results = pcoll | beam.ParDo(MyDoFn()).with_outputs(TAG_ERRORS, main='valid')
    _ = results['valid']      | 'Log'    >> beam.Map(...)
    _ = results[TAG_ERRORS]   | 'Errors' >> beam.Map(...)
    ```
  - **NEVER** do this — `main='valid'` names the main output, it does NOT register `'valid'` as a wrappable tag:
    ```python
    yield TaggedOutput('valid', record)   # WRONG: silently dropped, produces zero output
    ```
  - The `main=` keyword only sets the *attribute name* used to read the main output off the result (`results['valid']`). Inside `process`, the main output is always the untagged one.
